## 摘要

智算中心的核心矛盾正在从“算力资源是否充足”转向“已有算力能否稳定、低成本地转化为有效智能服务”。媒体援引中国信息通信研究院数据称，2025 年我国智能算力供应量约为 38 亿卡时，实际使用量约为 14 亿卡时，两者之比约为 36.8%[1]。这一数据反映了供需转化效率问题，但“卡时使用率”并不等同于单卡 GPU 利用率，也不能直接推导出所有智算中心的物理闲置比例。高端训练资源紧缺与部分推理资源低效并存，本质上是由芯片代际、显存与互联能力、软件栈适配、负载结构、区域需求及运营能力共同造成的结构性错配。

随着大模型应用从训练走向规模化推理，多数行业智算中心的主要任务不再是承接少数头部企业的前沿模型训练，而是运行开源或自有模型，为问答、知识库、流程自动化和智能体等应用提供推理服务。这类中心可以被理解为“Token 生产系统”：接收输入 Token，经过 Prefill 和 Decode 两个阶段，输出满足质量与时延要求的 Token。其运营目标不是单纯提高峰值 FLOPS 或设备平均利用率，而是在给定模型、硬件和业务约束下，持续提高**满足服务质量目标的有效吞吐（Goodput）**，降低单位有效 Token 的全生命周期成本与能耗。

本报告提出一套以业务负载为起点的算力运营方法：

1. **以需求为起点。** 将业务拆解为多轮 Agent、快速交互、长输出推理、高 QPS 小任务、RAG／文档问答和离线批处理六类典型负载，建立输入长度、输出长度、前缀复用、并发、突发性和 SLO 等负载画像。
2. **以 SLO 为约束。** 综合考察首 Token 时延（TTFT）、单输出 Token 时延（TPOT）、Token 间时延（ITL）、端到端时延（E2E）、尾延迟和结果质量，避免只追求原始吞吐量。
3. **以 Goodput 为统一指标。** 只统计同时满足时延、可用性和质量要求的请求或 Token，防止通过超载、排队或降低质量制造“高吞吐”。
4. **以全栈优化为手段。** 协同推进模型适配、并行策略、Prefill／Decode 资源组织、KV Cache 管理、连续批处理、缓存感知路由、准入控制和上游上下文治理。
5. **以持续运营形成闭环。** 建立“业务观测—基线测试—瓶颈定位—参数与架构优化—灰度验证—容量复盘”的机制，使优化能力沉淀为平台能力和标准操作流程。

算力运营的价值不在于某一次参数调优，而在于形成可测量、可复制、可审计、可持续演进的生产体系。

**关键词：** 智算中心；算力运营；大模型推理；Token 工厂；Goodput；SLO；KV Cache；Prefill／Decode；负载感知调度

## 1. 行业背景与问题界定

### 1.1 从“建设算力”转向“运营有效算力”

过去智算中心评价往往侧重设备数量、标称算力、机柜规模和建设进度。这些指标能够反映资产规模，却不能直接说明可持续交付的业务能力。推理服务真正消耗的是显存容量、显存带宽、卡间互联、主机内存、网络、供电和软件工程能力；用户真正感知的是响应速度、任务完成时间、服务稳定性和答案质量。

中国信通院产业与规划研究所 2026 年发布的《面向词元（Token）服务的智算基础设施发展研究报告（2026 年）》提出，智算基础设施的技术重心正在从峰值算力最大化转向每瓦 Token 产出提升，基础设施运营也在从资源租赁向 Token 服务运营转型[2]。这意味着算力中心的价值衡量需要从“拥有多少设备”转向“单位时间、单位成本和单位能耗能够交付多少合格服务”。

### 1.2 算力闲置不是单一过剩，而是结构性错配

当前行业同时存在两类现象：一部分高端、大规模、生态成熟的训练与推理资源供不应求；另一部分设备已经部署，却因模型不适配、软件不成熟、业务不足或服务不稳定而无法形成有效产能。二者并不矛盾。

主要错配包括：

| 错配维度               | 典型表现                                           | 对有效算力的影响                         |
| ---------------------- | -------------------------------------------------- | ---------------------------------------- |
| 需求与供给错配         | 先建设、后找业务，缺少稳定订单和真实负载           | 设备已到位但没有可持续任务               |
| 芯片代际与模型错配     | 显存容量不足、低精度格式不支持、互联能力不足       | 模型无法部署，或需要过度切分导致效率下降 |
| 硬件与软件栈错配       | 算子缺失、内核效率低、通信库或推理引擎适配不足     | 标称性能不能转化为实测性能               |
| 资源架构与负载错配     | 长输入、长输出、低延迟任务混合部署                 | Prefill 与 Decode 相互干扰，尾延迟恶化   |
| 区域供给与调用需求错配 | 算力远离用户，跨域网络、数据合规或服务接入成本较高 | 可售资源不等于可调用服务                 |
| 建设与运营错配         | 重采购轻调优，缺少 SRE、推理优化和业务运营能力     | 故障恢复慢、资源长期低效、客户流失       |

因此，解决算力闲置不能仅靠统一调度平台“把卡连起来”，也不能仅靠降价出租。必须把模型、负载、平台、网络、数据和服务运营作为同一个工程系统治理。

### 1.3 智算中心的两类典型定位

| 类型             | 主要任务                                 | 典型资源特征                                       | 核心能力                                     | 主要运营目标                                        |
| ---------------- | ---------------------------------------- | -------------------------------------------------- | -------------------------------------------- | --------------------------------------------------- |
| 训练与高端通用型 | 前沿模型预训练、后训练、大规模高并发推理 | 新一代高带宽加速卡，大规模高速互联，软硬件生态成熟 | 大规模分布式训练、容错、通信优化、集群稳定性 | 训练任务成功率、有效训练时长、集群作业效率          |
| 行业推理服务型   | 开源或自有模型推理，承载行业应用与智能体 | 数百至万卡不等，异构设备较多，模型与负载差异较大   | 模型适配、推理优化、SLO 保障、成本运营       | Goodput、单位 Token 成本、每瓦 Token 产出、服务质量 |

上述分类是运营定位的抽象，并不意味着某类设备必然闲置，也不意味着行业中心完全不能开展训练。关键在于：建设目标必须与实际订单、模型规模、软件生态和团队能力相匹配。本报告重点讨论第二类中心，以及第一类中心中的推理服务部分。

### 1.4 算力运营的核心命题

对推理型智算中心而言，算力运营可以概括为：

> **在设备与模型给定的条件下，根据真实业务特征确定 SLO，将负载控制在吞吐—延迟曲线的可用区间，通过调度、缓存、并行和资源架构移动性能拐点，最终以 Goodput、单位有效 Token 成本和每瓦有效 Token 产出衡量运营效果。**

“长上下文、高并发、低延迟”并非绝对不可同时实现，但在固定资源和固定模型下，三者通常存在显著工程权衡。运营工作的价值正是通过系统优化扩大可同时满足的范围，而不是脱离资源条件承诺单项指标最优。

## 2. 推理服务的技术基础与指标体系

### 2.1 从“算力工厂”到“Token 生产系统”

自回归大模型推理通常包括两个阶段：

- **Prefill（预填充）：** 并行处理输入 Prompt，计算各层注意力状态并生成 KV Cache，随后产生第一个输出 Token。长输入任务通常在该阶段形成较高计算压力。
- **Decode（解码）：** 基于已有上下文逐 Token 自回归生成结果。每步都需要读取模型参数和历史 KV Cache，常受到显存带宽、KV Cache 容量、批处理效率和跨卡通信影响。

Prefill 与 Decode 具有不同的资源特征。将二者简单混在同一资源池中，可能产生相互干扰：长 Prefill 请求进入后，正在执行的 Decode 序列可能出现生成停顿，导致 TPOT／ITL 尾延迟升高。Sarathi-Serve 对这一问题进行了系统分析，并提出 Chunked Prefill 与无停顿调度；DistServe 则通过 Prefill／Decode 分离和分阶段资源配置优化 Goodput[3][4]。Orca 的迭代级调度和 PagedAttention 的分页式显存管理，则分别为连续批处理与 KV Cache 高效管理奠定了重要基础[8][7]。

因此，推理平台不能仅按“一个模型部署若干副本”设计，而应把请求到达、排队、Prefill、KV 传输、Decode、流式返回、工具调用和缓存生命周期视为完整生产链。

### 2.2 PFLOPS 只是硬件能力的一项指标

PFLOPS 表示每秒千万亿次浮点运算，常用于描述理论峰值计算能力。使用这一指标时必须明确：

1. **数值精度。** FP64、FP32、TF32、FP16／BF16、FP8、FP4 的峰值不可直接横向比较。
2. **稠密与稀疏口径。** 部分厂商同时公布稠密和结构化稀疏性能，两者不能混用。
3. **计算单元口径。** CUDA Core、Tensor Core 或不同厂商的专用计算单元可能采用不同统计方式。
4. **设备粒度。** 单芯片、单加速卡、八卡服务器和超节点总算力必须分开。
5. **软件可用性。** 硬件支持某种精度，不代表目标模型、算子、推理引擎和精度方案已经成熟可用。
6. **可持续性能。** 功耗、散热、通信和内核效率会影响长时间运行表现。

对于大模型推理，除计算能力外，还应重点核验：

| 硬件维度         | 主要影响                                       | 规划时的核验重点                             |
| ---------------- | ---------------------------------------------- | -------------------------------------------- |
| 支持的数据类型   | 决定量化路径、Kernel 选择和精度方案            | 模型与引擎是否真正支持，精度损失是否可接受   |
| 显存容量         | 决定模型权重、KV Cache 和并发序列能否容纳      | 实际可用显存、运行时预留、碎片与多副本开销   |
| 显存带宽         | 影响 Decode 和权重／KV 读取效率                | 实测带宽及目标模型下的有效利用率             |
| 卡内／卡间互联   | 影响 TP、EP 和 P／D 分离的通信成本             | 单向／双向口径、拓扑、并发通信与延迟         |
| 跨节点网络       | 影响多节点推理、KV 传输和资源池扩展            | RDMA 能力、拥塞控制、实际带宽与尾延迟        |
| 主机与存储       | 影响 Tokenization、调度、KV Offload 和模型加载 | CPU、内存、PCIe、NVMe 是否形成新瓶颈         |
| 功耗与散热       | 决定持续运行、机柜密度和单位能耗产出           | 整机功耗而非仅芯片 TDP，包含网络与制冷       |
| 软件栈与运维工具 | 决定适配周期、稳定性和故障定位效率             | 算子覆盖、Profiler、监控、升级兼容和厂商支持 |

对 B300、A100、Ascend 950DT、Ascend 910B2 等不同设备，不宜只用一组峰值 FLOPS 排列优劣。项目应基于**准确到板卡和整机型号的规格书**，建立同口径参数表，再用目标模型和真实负载完成实测。以 Ascend 950DT 为例，华为公开发布资料将其定位为面向 Decode 和训练的芯片，并单独披露显存容量、显存带宽和互联带宽，正体现了推理硬件多维评价的重要性[5]。

### 2.3 使用方关注的体验与质量指标

| 指标                 | 定义                                       | 主要用途                                        |
| -------------------- | ------------------------------------------ | ----------------------------------------------- |
| TTFT                 | 从请求到达到收到首个输出 Token 的时间      | 衡量首次响应速度，受排队、预处理和 Prefill 影响 |
| TPOT                 | 首 Token 之后，平均每个输出 Token 的耗时   | 衡量流式输出平均速度                            |
| ITL／TBT             | 相邻输出 Token 的时间间隔                  | 识别输出抖动与生成停顿                          |
| E2E Latency          | 从请求到达到完整结果返回的时间             | 衡量单次请求整体完成时间                        |
| P50／P95／P99        | 指标分布的中位数及尾部分位数               | 避免平均值掩盖长尾体验                          |
| Task Completion Time | 一个完整业务任务的完成时间                 | 适用于多轮 Agent 和工具调用场景                 |
| Quality              | 准确率、任务成功率、格式合规率、人工评分等 | 防止以牺牲结果质量换取速度                      |
| Availability         | 服务可用时间与约定服务时间之比             | 衡量持续服务能力                                |

常用关系为：

$$
TPOT=\frac{T_{E2E}-T_{TTFT}}{N_{out}-1}\quad (N_{out}>1)
$$

$$
T_{E2E}=T_{TTFT}+\sum_{k=2}^{N_{out}}ITL_k
$$

TTFT 应在网关、推理引擎和业务侧统一起止点；E2E 还应明确是否包含网络传输、检索、内容审核和后处理。不同口径的数据不能直接比较。

### 2.4 运营方关注的效率、成本与稳定性指标

| 指标                  | 建议定义                                  | 注意事项                                 |
| --------------------- | ----------------------------------------- | ---------------------------------------- |
| 请求吞吐量            | 单位时间完成的请求数                      | 必须附带输入／输出长度分布               |
| 输入／输出 Token 吞吐 | 单位时间处理的输入或输出 Token 数         | 两者应分别统计，避免混为总 Token         |
| 每卡吞吐              | 集群吞吐除以实际参与服务的加速卡数        | 明确是否包含冗余与备用资源               |
| 最大有效并发          | 满足 SLO 与质量约束时可持续承载的并发数   | 不等于引擎允许的最大序列数               |
| 排队时间              | 请求进入系统至开始执行的时间              | 高负载下是尾延迟的重要来源               |
| SLO 达标率            | 满足约定 TTFT、TPOT、E2E 等条件的请求占比 | 应同时设置质量门槛                       |
| Prefix Cache 命中率   | 可复用前缀 Token 占总输入 Token 的比例    | “缓存块命中数”与“Token 级复用率”应分开   |
| KV Cache 占用与换出   | KV 显存占用、Offload、换入换出和抢占情况  | 反映长上下文与高并发压力                 |
| 加速卡活跃度          | 设备执行有效工作的时间比例                | 不等于 SM 利用率，也不等于业务利用率     |
| 单位有效 Token 成本   | 统计期总成本／合格输出 Token 数           | 成本应包含折旧、能耗、网络、运维和软件等 |
| 每瓦有效 Token 产出   | 合格输出 Token 数／系统能耗               | 应采用统一计量边界                       |
| 故障与恢复            | 失败率、MTTR、任务重试率、副本重建时间    | 大模型服务需关注慢节点和隐性故障         |

单位成本可采用下式：

$$
Cost_{1M\ valid\ tokens}=\frac{C_{hardware}+C_{energy}+C_{network}+C_{software}+C_{labor}+C_{facility}+C_{other}}{N_{valid\ output\ tokens}}\times10^6
$$

其中，成本口径可按财务全成本或运营现金成本分别计算，但必须保持一致。若只统计输出 Token，应明确输入处理成本已分摊到输出 Token；若采用输入、输出分别计价，则应分别建立成本模型。

### 2.5 以 Goodput 统一体验与效率

原始吞吐量只回答“系统生成了多少”，Goodput 回答“系统合格地交付了多少”。可按请求或 Token 定义：

$$
Goodput_{req}=\frac{\sum_{i=1}^{N}\mathbb{1}(request_i\ meets\ SLO\land quality)}{T}
$$

$$
Goodput_{token}=\frac{\sum_{i=1}^{N}N_{out,i}\cdot\mathbb{1}(request_i\ meets\ SLO\land quality)}{T}
$$

其中，指示函数表示只有满足时延、完整性和质量要求的请求才计入。实际平台还可增加可用性、租户公平性和安全合规条件。

Goodput 不是取代所有指标，而是作为容量与优化验收的统一结果指标。TTFT、TPOT、排队时间、显存、功耗等指标仍用于解释瓶颈和指导调优。

### 2.6 建立分层利用率口径

行业讨论中“利用率”经常混用，建议至少区分：

1. **设施上架率：** 已安装设备占规划或已建机柜能力的比例。
2. **资源分配率：** 已分配给租户或任务的资源占可运营资源的比例。
3. **时间活跃率：** 设备在统计期内处于非空闲状态的时间比例。
4. **硬件执行利用率：** SM、NPU 核心、显存带宽等硬件计数器指标。
5. **业务有效利用率：** 满足 SLO 与质量要求的有效工作量占理论或实测可用产能的比例。

高 SM 利用率可能来自低价值重试或无效计算；低平均利用率也可能是为在线峰值和尾延迟预留容量。运营评价应以业务有效利用率为最终结果，以其他指标作为诊断依据。

## 3. 需求分析与负载建模

### 3.1 从业务清单拆解模型请求

需求分析不能停留在“部署哪些模型、服务哪些应用”。同一个应用可能同时产生多种推理负载。例如，一个复杂 Agent 可能先由高 QPS 小模型完成路由，再执行 RAG 检索，随后进行长上下文规划，最后生成短结果。因此，应先梳理业务，再拆解请求链，最后形成资源需求。

典型智能体业务可分为三类：

| 业务类型   | 示例一                     | 示例二                             | 主要推理特征                                            |
| ---------- | -------------------------- | ---------------------------------- | ------------------------------------------------------- |
| 问答助手类 | 企业知识库问答             | 客服与政策咨询助手                 | 交互频繁，常结合 RAG，关注 TTFT、回答质量和引用准确性   |
| 流程处理类 | 合同／票据／公文审核       | 工单分类、流转与材料生成           | 请求链较固定，可能包含分类、抽取、校验和报告生成        |
| 自主执行类 | AI Coding 与软件工程 Agent | 浏览器操作、数据研究与复杂任务执行 | 多轮调用、长上下文、工具等待明显，关注任务 E2E 和成功率 |

模型选择应服从任务需求，而不是追求模型版本清单。每个候选模型都应通过质量、上下文、吞吐、硬件适配、许可合规和综合成本评估；对路由、分类、审核等小任务，应优先评估更小的专用模型是否已能满足质量要求。

### 3.2 六类典型推理负载

| 场景                  | 典型业务                        | 核心特征                             | 首要优化目标                     |
| --------------------- | ------------------------------- | ------------------------------------ | -------------------------------- |
| 多轮 Agent／AI Coding | AI 编程、工具调用、自主任务执行 | 长上下文、前缀高度复用、多轮间歇调用 | KV 复用、任务 E2E、任务吞吐      |
| 快速交互              | Chat、实时问答、交互助手        | 短上下文、低延迟、高交互频率         | TTFT、TPOT、P95／P99             |
| 内容生成／深度推理    | 报告、研究、长文、复杂推理      | 中长输入、长输出、质量优先           | Decode 吞吐、E2E、质量           |
| 高 QPS 小任务         | Router、Judge、分类、决策       | 短输入、极短输出、高请求频率         | Requests/s、TTFT、调度效率       |
| RAG／文档问答         | 知识库问答、文档分析、检索增强  | 长输入、短输出、前缀复用通常不稳定   | Prefill 吞吐、上下文有效信息密度 |
| 离线批处理            | 数据合成、模型评测、批量生成    | 无在线延迟要求，可充分批处理         | 总吞吐、设备有效利用率、单位成本 |

这六类并非互斥的业务标签，而是六种**负载原型（Workload Archetypes）**。运营系统应允许一个应用被拆解为多个负载原型，并分别路由、容量规划和验收。

### 3.3 负载向量

对每一类请求建立负载向量：

$$
W=(L_{in},L_{out},H_{prefix},C,B,S_{TTFT},S_{TPOT},Q)
$$

| 维度           | 含义                               | 对系统的主要影响                 |
| -------------- | ---------------------------------- | -------------------------------- |
| \(L_{in}\)     | 输入长度及其分布                   | 决定 Prefill 压力和 KV 初始占用  |
| \(L_{out}\)    | 输出长度及其分布                   | 决定 Decode 压力和资源占用时长   |
| \(H_{prefix}\) | Prefix Cache 命中情况              | 决定实际可节省的 Prefill 工作量  |
| \(C\)          | 并发度及活跃序列数                 | 决定 Batching 收益与 KV 容量压力 |
| \(B\)          | 突发性、到达过程与峰谷比           | 决定排队、弹性扩容与 P99         |
| \(S_{TTFT}\)   | 首 Token 时延目标                  | 影响 Prefill 调度与准入控制      |
| \(S_{TPOT}\)   | 单 Token 输出时延目标              | 影响 Decode Batch 和资源隔离     |
| \(Q\)          | 质量、准确率、格式和任务成功率要求 | 约束模型、量化、采样和推理预算   |

建议同时使用两个比例：

$$
R_{IO}=\frac{L_{in}}{L_{out}}
$$

用于初步判断 Prefill 与 Decode 的相对压力；

$$
R_{reuse}=\frac{L_{cached}}{L_{in}}
$$

用于衡量前缀复用程度。两者都应基于分布而非仅使用平均值，尤其要保留 P50、P95、P99 和最大值。

对多轮 Agent，还应记录：

- \(N_{turns}\)：完成一个任务所需的模型调用轮数；
- \(T_{tool,j}\)：第 \(j\) 次工具执行及等待时间；
- \(T_{orchestration}\)：编排、状态管理和其他控制开销；
- 任务成功率、无效重试率、工具调用失败率。

任务完成时间为：

$$
T_{task}=\sum_{i=1}^{N_{turns}}T_{LLM,i}+\sum_jT_{tool,j}+T_{orchestration}
$$

因此，优化单次推理并不必然成比例改善 Agent 任务 E2E。如果工具执行或无效重试占主要时间，应优先优化工具并发、任务规划和上下文策略。

### 3.4 负载采集与脱敏

建议采集以下字段形成可回放轨迹：时间戳、租户、业务类型、模型与版本、输入／输出 Token 数、上下文轮次、缓存命中、排队时间、TTFT、ITL、E2E、完成状态、质量标签、资源实例、并行配置、工具等待时间和错误类型。

负载数据应进行租户隔离和脱敏，原则上优先保存长度、时序和统计特征，不将业务正文、个人信息或商业秘密纳入性能分析平台。用于回放的数据集应覆盖正常流量、峰值、突发、长上下文、异常长输出和失败重试等情形。

## 4. 可运营智算平台的总体架构

### 4.1 平台组成

一个可运营的智算平台至少包括七层能力：

| 层级         | 核心组件                                           | 运营要求                                       |
| ------------ | -------------------------------------------------- | ---------------------------------------------- |
| 资源层       | 加速卡、服务器、网络、存储、供电与制冷             | 统一资产台账、拓扑可见、健康检查、固件管理     |
| 资源管理层   | 容器／虚拟化、集群调度、队列、配额、弹性伸缩       | 支持异构资源标签、隔离、碎片治理和容量预留     |
| 推理运行时层 | 推理引擎、模型仓库、并行执行、KV Cache、量化与内核 | 版本可追踪、性能可复现、模型兼容可验证         |
| 服务调度层   | API 网关、智能路由、负载均衡、准入控制、限流与降级 | 按负载和 SLO 路由，避免平均分配流量            |
| 可观测层     | Metrics、Logs、Tracing、Profiling、能耗与成本计量  | 从业务请求贯通至设备和内核，统一指标口径       |
| 运营管理层   | SLO、容量、变更、故障、成本、计费、客户与工单      | 建立闭环流程、审计记录和责任边界               |
| 安全合规层   | 身份权限、租户隔离、数据保护、模型与内容安全       | 最小权限、传输与存储保护、日志脱敏、供应链治理 |

典型请求链路为：

```text
业务应用／Agent
      │
      ▼
API 网关：认证、配额、限流、审计
      │
      ▼
负载识别与智能路由：模型、输入／输出预测、SLO、缓存亲和性
      │
      ▼
全局调度与准入控制：排队、优先级、资源预留、降级
      │
      ├── Prefill 资源池 ── KV Cache 传输／分层存储 ──┐
      │                                                ▼
      └── 共置推理实例 ──────────────────────── Decode 资源池
                                                     │
                                                     ▼
                                           流式返回／后处理／质量评估
                                                     │
                                                     ▼
                                        观测、成本计量与容量反馈
```

P／D 分离不是唯一架构。中小规模或负载较单一时，共置实例配合 Chunked Prefill 和合理调度可能更简单、更经济；长输入、高并发、明显干扰或需要独立扩缩容时，再评估分离架构。

### 4.2 五类系统级优化手段

#### （1）Prefill／Decode 资源组织

可选路径包括：

- **共置优化：** 使用 Continuous Batching、Chunked Prefill 和 Token Budget，控制长 Prefill 对 Decode 的干扰。
- **物理分离：** Prefill 池与 Decode 池独立部署、独立并行和独立扩缩容。
- **逻辑隔离：** 在统一资源层上按实例、队列或时间片进行隔离，作为复杂度和收益之间的折中。

P／D 分离的收益必须与 KV 传输、网络拥塞、资源碎片和运维复杂度一起评估。DistServe 的研究说明，分离架构需要联合优化两阶段的资源配置、并行策略和放置方式，而非简单把实例拆成两组[3]。

#### （2）KV Cache 全生命周期管理

主要措施包括：

- Automatic Prefix Caching 与跨请求公共前缀复用；
- 会话亲和性和 Cache-aware Routing，避免请求被随机路由到无缓存副本；
- 按业务价值设计保留、淘汰和预取策略；
- 在显存、主机内存和分布式存储之间实施分层 Offload；
- 管理多轮 Agent 在工具等待期间的 KV 保留与释放；
- 对 KV 量化、传输和远程复用开展精度与性能验证。

Mooncake 的 KVCache-centric 架构表明，缓存位置、全局调度和 P／D 资源选择需要联合设计[6]。但缓存容量越大并不必然越好：跨层读取和网络传输成本可能抵消重复 Prefill 节省的收益，必须比较“重算成本”和“读取成本”。

#### （3）多级调度与准入控制

调度策略至少应覆盖：

- 业务优先级、租户配额与公平性；
- 动态 Batch、Active Sequence 和 Token Budget；
- TTFT／TPOT 分目标调度；
- 基于剩余 SLO 预算的排队与准入；
- 在线、离线和可延迟任务混合时的资源预留；
- 过载时限流、排队、降级或快速失败，防止系统进入吞吐崩溃区。

在接近容量拐点后，继续增加请求往往只会增加排队和尾延迟，甚至导致重试风暴。准入控制是保障 Goodput 的必要组件，而不是服务能力的消极限制。

#### （4）Workload 感知路由

路由决策应综合：

- 目标模型及版本；
- 输入长度、预测输出长度和上下文类型；
- Prefix Cache 分布与会话亲和性；
- TTFT、TPOT、E2E 和租户优先级；
- 实例排队长度、活跃序列、KV 可用空间和硬件拓扑；
- 资源池专用化程度及跨池迁移成本。

核心原则是：**让具有相似资源特征和缓存局部性的请求尽量进入合适的专用资源池，同时避免单纯按会话粘连造成热点。**

#### （5）结合上游减少无效 Token

系统层优化不能替代业务侧治理。应同步推进：

- Prompt 模板规范化，固定 System Prompt、工具定义和示例顺序；
- 文档去重、切分优化、Context Pruning 和 Prompt Compression；
- 检索 Reranking、动态 Top-K 与上下文预算控制；
- 限制无效反思、重复调用和异常长输出；
- 通过模型分级，让 Router、Judge、分类等任务使用足够但不过度的模型；
- 对失败请求设置重试上限与幂等策略，避免重复消耗。

减少无效输入与输出，往往比单纯扩大 Batch 更能同时改善成本、时延和质量。

### 4.3 模型部署与并行策略规划

模型部署首先进行显存估算。权重基础占用可粗略表示为：

$$
M_{weights}\approx \frac{P\times b_{weight}}{8}
$$

其中，\(P\) 为参数数量，\(b_{weight}\) 为每参数字节数。实际部署还需考虑运行时工作区、激活、通信缓冲、碎片和副本开销。

传统 Transformer 的 KV Cache 可按模型结构估算，单 Token 的理论量级为：

$$
M_{KV/token}\approx 2\times N_{layer}\times N_{kv\_head}\times D_{head}\times b_{kv}
$$

再乘以上下文长度和活跃序列数。GQA、MQA、MLA、滑窗注意力和 KV 量化会显著改变该结果，因此必须以具体模型结构和引擎实现为准。

| 并行方式         | 适用目的                           | 主要代价与风险                      |
| ---------------- | ---------------------------------- | ----------------------------------- |
| 数据并行（DP）   | 增加模型副本和整体吞吐             | 每副本重复占用权重，需做好负载均衡  |
| 张量并行（TP）   | 单副本容纳更大模型或降低单请求时延 | 高频集通信，对卡间互联敏感          |
| 流水线并行（PP） | 跨节点切分层，扩大可部署模型规模   | 气泡、微批次调度和尾延迟问题        |
| 专家并行（EP）   | 部署 MoE 模型并分布专家            | All-to-All 通信、专家负载不均和热点 |
| 序列／上下文并行 | 支持超长上下文                     | 实现依赖强，通信与算子适配复杂      |

规划顺序应为：先满足模型质量与显存可行性，再比较并行方案的实测吞吐和时延，最后确定副本数与资源池配比。不能仅依据经验把高 TP 或高 EP 作为默认方案；对于短小任务，过高通信并行可能降低效率。

### 4.4 国产与异构算力的软件适配

异构算力释放的关键不只是统一 API，而是建立从模型到硬件的完整验证链：

1. **模型兼容：** 检查模型结构、Tokenizer、算子、注意力变体和量化格式支持。
2. **引擎适配：** 验证推理引擎、连续批处理、前缀缓存、Chunked Prefill、推测解码等能力。
3. **内核优化：** 分析热点算子、内存访问、Kernel Launch 和图执行效率。
4. **通信优化：** 验证 TP／PP／EP、RDMA、集合通信和 KV 传输性能。
5. **质量验证：** 对量化、图优化和算子替换开展精度回归，不允许只测速度。
6. **稳定性验证：** 进行长时间压测、故障注入、慢节点检测和版本升级回退。
7. **可观测性：** 建立跨驱动、运行时、引擎和业务的统一诊断能力。

对设备“相当于另一款产品多少比例”“只能支持到某个模型版本”等结论，如果没有固定模型、精度、上下文、并发、SLO 和软件版本，不应作为通用事实。应改为项目内的可比实测结果，并记录完整测试条件。

## 5. 六类负载的专项优化方法

### 5.1 多轮 Agent／AI Coding：长上下文与高前缀复用

**典型特征**

- 上下文可能达到数十万 Token，并随任务推进持续增长；
- 单轮通常输入大于输出，完整任务包含多轮模型与工具调用；
- System Prompt、工具定义、代码仓库上下文和历史消息具有较高复用潜力；
- 工具执行导致请求间歇性和突发性；
- 用户更关注任务完成时间和成功率，运营方关注单位设备时间完成的任务数。

**核心瓶颈：** 重复 Prefill、KV Cache 容量与生命周期、缓存亲和性、工具等待期间资源占用以及无效重试。

| 优化层级   | 主要措施                                        | 验证指标                         |
| ---------- | ----------------------------------------------- | -------------------------------- |
| Prompt 层  | Canonicalization、稳定前缀、固定工具定义顺序    | Token 级前缀复用率、上下文长度   |
| KV 层      | Prefix Caching、分层保留、淘汰、Offload、量化   | 命中率、读取时延、显存占用、质量 |
| 调度层     | Cache-aware Routing、Session Affinity、热点均衡 | 实际命中率、实例负载差异         |
| Prefill 层 | Chunked Prefill、合理 Token Budget、并行优化    | TTFT、Prefill tok/s、Decode 干扰 |
| 并发层     | Continuous Batching、动态并发与准入控制         | 任务 Goodput、P99、抢占次数      |
| Agent 层   | 工具等待时 KV 策略、调用去重、规划与重试优化    | 任务 E2E、调用轮数、任务成功率   |

**实施重点：** 缓存优化应以端到端任务为边界。若为了提高单请求缓存命中率而长期占用大量显存，可能降低整体任务 Goodput。

### 5.2 快速交互：低延迟敏感型负载

**典型特征**

- 输入和输出相对较短，交互频率高；
- 用户高度关注 TTFT、流式输出流畅度和 E2E；
- P95／P99 尾延迟比平均吞吐更重要；
- 高峰突发容易形成排队，长 Prefill 混入会放大输出停顿。

**核心瓶颈：** 排队、调度与 CPU 前处理开销、Prefill／Decode 干扰和过载重试。

主要措施：

1. 设置独立低延迟资源池或高优先级队列；
2. 限制 Active Sequence 和 Batch，避免为追求吞吐牺牲尾延迟；
3. 使用 Chunked Prefill、Priority Scheduling 和 Admission Control；
4. 采用图执行或等效机制减少 Kernel Launch 开销，并验证兼容性；
5. 优化 Tokenization、API Server、网络序列化和流式返回链路；
6. 为峰值预留容量，设置明确的限流与降级策略。

**核心评价：** TTFT P50／P95／P99、TPOT／ITL P99、E2E P99、SLO Goodput、拒绝率与重试率。

### 5.3 内容生成／深度推理：长输出与 Decode 密集

**典型特征**

- 输出可达数千至数万 Token，资源占用时间长；
- 对 TTFT 相对不敏感，但关注生成速度、任务 E2E 和质量；
- 长输出增加 KV Cache 生命周期，并可能形成长尾任务；
- MoE 模型还可能受到专家通信和负载不均影响。

**核心瓶颈：** Decode 吞吐、显存带宽、KV 容量、通信和长尾调度。

主要措施：

- 在质量可接受且接受率合适时采用 Speculative Decoding、MTP 等技术；
- 优化 Decode-oriented Batching 和图执行；
- 优化 TP／EP 拓扑、MoE All-to-All 和计算通信重叠；
- 评估 KV 量化、容量规划、抢占与换出成本；
- 使用独立 Decode Pool 或调整 P／D 配比；
- 对异常长输出设置业务预算，避免单个请求长期挤占资源。

**核心评价：** 输出 Token/s、每卡 Decode 吞吐、E2E、质量、KV 占用、抢占次数和单位有效输出 Token 成本。推测解码必须同时报告接受率及其对整体 Goodput 的净收益。

### 5.4 高 QPS 小任务：调度与固定开销敏感

**典型特征**

- 输入短、输出通常仅几个到几十个 Token；
- 请求频率高，单次模型计算量较小；
- 调度、API、Tokenization、Kernel Launch 和通信固定成本占比高；
- 常见于 Agent 内部 Router、Judge、工具选择、分类和审核。

**核心瓶颈：** 系统固定开销而非单纯模型计算。

主要措施：

1. 使用高效 Continuous Batching，合并可兼容的小请求；
2. 优化 CPU Pipeline、Tokenization 和 API Server 并发；
3. 采用图执行等方式减少单请求固定开销；
4. 避免对极短任务使用过高 TP／EP，降低通信成本；
5. 在质量达标时使用更小专用模型或合并多个判定任务；
6. 对重复判定使用结果缓存，但需防止缓存语义错误。

**核心评价：** Requests/s、TTFT、CPU 占用、单请求调度成本、每卡请求 Goodput 和结果准确率。

### 5.5 RAG／文档问答：长输入与 Prefill 密集

**典型特征**

- 输入从数千到数十万 Token 不等，输出相对较短；
- 检索文档随问题变化，公共前缀复用可能低于稳定会话 Agent；
- 无效或低相关上下文会同时增加成本并损害回答质量；
- 长 Prefill 易干扰同池在线 Decode 请求。

**核心瓶颈：** Prefill 计算、上下文有效信息密度、检索质量和长文档调度。

主要措施：

- 使用 Chunked Prefill 并优化 Prefill 吞吐；
- 通过 Context Pruning、Prompt Compression、去重和切分优化减少无效输入；
- 使用 Reranking 和动态 Top-K，按问题复杂度控制上下文预算；
- 缓存固定 System Prompt、稳定文档前缀和可复用内容；
- 高负载下设置 Prefill 专用资源或独立长输入队列；
- 将检索、重排、生成和引用校验分段观测，避免把所有时延归因于模型。

**核心评价：** Prefill tok/s、TTFT、E2E、输入 Token 数、有效上下文比例、回答质量与引用准确性。

### 5.6 离线批处理：吞吐与成本优先

**典型特征**

- 对 TTFT 基本无要求，可容忍较长排队；
- 可提前组织数据、排序和调度；
- 输入输出比例差异较大，任务完成时间允许较长；
- 适合与在线业务进行峰谷互补，但必须防止干扰在线 SLO。

**核心瓶颈：** 批处理效率、长短任务不均、资源碎片、计算通信效率和失败重跑。

主要措施：

1. 增大合理的 `max_num_batched_tokens` 和 Active Sequence；
2. 按输入／输出长度分桶，减少 Padding 和长尾；
3. 使用 DP 扩展，并优化 TP／EP 配置；
4. 采用检查点、断点续跑和幂等任务设计；
5. 与在线负载分池或通过配额、时间窗和优先级隔离；
6. 按任务完成成本而非单纯设备忙碌程度评价。

**核心评价：** Tokens/s/GPU、Requests/h、任务完成时间、失败重跑率、Cost/1M valid tokens 和 Tokens/kWh。

## 6. 日常运营体系

### 6.1 算力运营的四个基本问题

| 基本问题                       | 回答要点                                                     |
| ------------------------------ | ------------------------------------------------------------ |
| 一个可运营平台由哪些要素构成？ | 资源、集群管理、推理运行时、服务调度、可观测、运营管理和安全合规七层能力 |
| 是否经历完整生命周期？         | 必须贯通需求、规划、设计、建设、测试、上线、运营、扩容和退役，不能把交付设备视为项目结束 |
| 日常运营哪些工作最多？         | 告警与故障处理、容量与排队分析、模型及版本变更、性能调优、客户负载分析、成本复盘和安全审计 |
| 需要什么技能人员？             | 平台与 SRE、推理引擎与内核优化、模型适配、网络与硬件、可观测与数据、业务解决方案、安全与成本运营等复合能力 |

### 6.2 日常运营事项

#### （1）服务与 SLO 运营

- 按租户和业务维护 SLO，不使用单一集群平均值替代客户体验；
- 监控 TTFT、TPOT、E2E、错误率、SLO 达标率和 Goodput；
- 对慢请求建立从网关到推理实例、内核和网络的 Trace；
- 建立过载、长上下文、异常输出和重试风暴预案。

#### （2）容量与资源运营

- 按负载原型统计峰谷、并发、输入输出长度和缓存命中；
- 维护各模型、各资源池的吞吐—延迟曲线和容量拐点；
- 处理资源碎片、空闲副本、低效益模型和热点实例；
- 区分在线保障容量、离线可抢占容量、冗余容量和维修容量；
- 根据业务轨迹调整 P／D 配比、副本数、并行方式和专用池规模。

#### （3）变更与发布运营

模型、Tokenizer、推理引擎、驱动、固件、通信库和内核变更都可能影响性能与质量。每次变更应具备：

1. 版本清单和兼容性说明；
2. 质量回归和性能基线；
3. 灰度、观察期与自动或人工回退条件；
4. 配置快照和可复现部署；
5. 变更后 SLO、成本与稳定性复盘。

#### （4）可靠性与故障运营

除设备离线外，还应重点识别慢节点、通信降速、显存异常、KV 泄漏、请求悬挂和结果质量漂移。建立故障分级、值班升级、备件、根因分析和问题闭环机制。核心指标包括故障率、MTTR、重复故障率、服务恢复时间和任务重试成本。

#### （5）成本与能耗运营

- 按模型、租户、业务和资源池归集成本；
- 将折旧、供电、制冷、网络、软件、运维和闲置容量纳入统一视图；
- 同时跟踪单位有效 Token 成本和每瓦有效 Token 产出；
- 识别“高利用但低价值”的无效重试、异常生成和低质量输出；
- 通过离线调度、模型分级、容量整合和上游 Token 治理降本，而非简单压低在线冗余。

#### （6）安全与合规运营

建立租户隔离、密钥管理、模型与镜像供应链治理、日志脱敏、提示词与输出安全、数据留存策略以及跨域调用审计。性能追踪和负载回放不得成为敏感数据无序汇集的通道。

### 6.3 团队能力配置

| 角色               | 核心职责                                      |
| ------------------ | --------------------------------------------- |
| 平台架构与资源管理 | 总体架构、异构资源、容量和平台演进            |
| SRE／运维工程      | 可用性、监控、值班、故障、变更与自动化        |
| 推理系统优化       | 引擎、调度、KV Cache、并行、P／D 和性能分析   |
| 模型适配与质量工程 | 模型部署、量化、算子适配、质量评估和回归      |
| 网络与硬件工程     | 拓扑、RDMA、服务器、固件、功耗和硬件故障      |
| 数据与可观测工程   | 指标、Trace、负载画像、成本数据和实验平台     |
| 业务解决方案       | 应用拆解、Agent／RAG 优化、SLO 协商和客户赋能 |
| 安全与运营治理     | 权限、合规、计费、资产、供应商与成本管理      |

团队规模应随集群规模、异构程度、服务时间和客户数量确定，但上述能力不能因团队精简而完全缺位。

## 7. 性能测试与持续优化方法

### 7.1 建立可复现基线

每次测试必须固定并记录：

- 模型、权重版本、Tokenizer 和质量配置；
- 硬件、服务器、网络拓扑、驱动与固件；
- 推理引擎、运行时、通信库和关键内核版本；
- 精度、量化、TP／PP／EP／DP、副本数；
- Batch、Active Sequence、Token Budget、缓存和调度参数；
- 输入／输出长度分布、前缀复用、到达过程、并发和测试时长；
- TTFT、TPOT、E2E、Goodput、质量、功耗及成本口径。

没有这些条件的“吞吐提升多少倍”不具备可复现性，也不适合用于跨平台采购或验收。

### 7.2 负载测试步骤

1. **正确性检查：** 验证模型输出、流式协议、异常处理和质量基线。
2. **单请求剖面：** 测量不同输入／输出长度下的基础时延和资源消耗。
3. **并发扫描：** 阶梯式增加并发或到达率，记录吞吐、排队和尾延迟。
4. **曲线识别：** 找到吞吐增长明显放缓、尾延迟快速上升的区域。
5. **SLO 容量确定：** 以 Goodput 和 SLO 达标率确定可持续容量，而非以系统未崩溃为上限。
6. **突发与 soak 测试：** 验证峰值、长稳、缓存退化、内存泄漏和故障恢复。
7. **优化对照：** 每次尽量只改变主要变量，保留对照组和统计波动。
8. **灰度上线：** 用真实业务轨迹复核实验结论，再逐步扩大流量。

### 7.3 优化闭环

```text
真实业务轨迹
   ↓
负载画像与瓶颈假设
   ↓
可复现实验与对照测试
   ↓
参数／调度／架构／上游联合优化
   ↓
质量、性能、稳定性、成本四维验收
   ↓
灰度发布与持续观测
   ↓
容量模型和标准配置更新
   └──────────────────→ 返回真实业务轨迹
```

性能研究可以提供收益量级参考，但不能直接替代本地验证。例如，Sarathi-Serve 在其特定模型、硬件与基线下报告了服务能力提升，DistServe 也在其评测条件下展示了 Goodput 优势[3][4]。这些结果说明架构优化具有显著潜力，但不能推导出任意生产集群都能获得相同倍数。原大纲中“专业运营优化与未优化总体吞吐量相差 6—10 倍”的说法，宜作为待验证假设，而不宜作为通用承诺。

### 7.4 优化收益的统一验收

建议采用以下收益表达：

$$
Improvement_{goodput}=\frac{Goodput_{optimized}-Goodput_{baseline}}{Goodput_{baseline}}
$$

同时要求：

- 质量不低于约定门槛；
- SLO 达标率不下降；
- 统计置信与多次重复结果可接受；
- 长稳测试无显著资源泄漏或性能衰减；
- 成本与能耗收益不被额外资源、网络和运维开销抵消。

最终报告应同时给出基线、优化后结果、测试条件和适用范围，而不是只给一个提升倍数。

## 8. 建设与运营实施路线

### 阶段一：现状评估与需求基线

**主要工作**

- 盘点设备、拓扑、软件栈、模型、合同和真实业务；
- 统一利用率、吞吐、成本和质量口径；
- 采集并回放典型负载；
- 建立现状基线和问题清单。

**交付物**

- 资产与软件版本台账；
- 业务—模型—请求链映射；
- 六类负载画像；
- 当前 Goodput、SLO、成本与能耗基线；
- 可快速治理的问题和结构性问题清单。

### 阶段二：平台底座与可观测建设

**主要工作**

- 建立模型仓库、版本管理、资源标签和配置管理；
- 部署网关、排队、限流、配额和基础路由；
- 打通业务、引擎、资源、网络、能耗和成本观测；
- 建立质量回归、压测、灰度和回退机制。

**交付物**

- 可运营的推理服务平台；
- 统一指标字典和监控看板；
- 标准部署与变更流程；
- 测试数据集和基线报告。

### 阶段三：重点场景专项优化

优先选择业务量大、瓶颈明确、收益可测的场景，不追求同时铺开所有技术：

1. 多轮 Agent：优先前缀复用、缓存路由和任务 E2E；
2. 快速交互：优先尾延迟、资源隔离和准入控制；
3. RAG：优先上下文治理与 Prefill 优化；
4. 长输出：优先 Decode 吞吐和 KV 容量；
5. 高 QPS 小任务：优先小模型和固定开销；
6. 离线任务：优先批处理、长度分桶和峰谷调度。

**交付物**

- 每个场景的对照实验与优化报告；
- 标准参数包和资源池配置；
- 业务侧优化建议；
- 经 Goodput、质量、成本和稳定性共同验收的收益结论。

### 阶段四：智能调度与规模化运营

**主要工作**

- 根据实时负载和历史轨迹实施 Workload 感知路由；
- 动态调整副本、P／D 配比、缓存和在线／离线配额；
- 建立跨模型、跨资源池的成本与容量优化；
- 将成熟优化固化为自动化策略和标准运营流程。

**交付物**

- 智能路由与容量策略；
- 模型级、业务级、租户级运营报表；
- 周期性容量复盘和设备退役／升级建议；
- 可持续迭代的运营知识库。

- 不以峰值 FLOPS 代替有效服务能力；

- 不以单次实验代替长稳与真实业务验证；
- 不以吞吐提升掩盖质量、成本或尾延迟恶化。

## 10. 主要风险与实施边界

| 风险                   | 典型后果                                | 控制措施                                       |
| ---------------------- | --------------------------------------- | ---------------------------------------------- |
| 需求预测失真           | 建设规模与真实业务不匹配                | 以订单和负载基线分阶段扩容，保留可调整资源池   |
| 指标口径混乱           | 上架率、出租率、GPU 利用率相互误读      | 建立指标字典，所有报表注明边界、公式和统计周期 |
| 过度架构复杂化         | P／D 分离、跨层缓存和智能路由增加故障面 | 以实测收益分阶段引入，保留简单可回退架构       |
| 只优化硬件参数         | 引擎忙碌但业务 Goodput 不升反降         | 从业务 SLO 反推优化，验收最终有效产出          |
| 缓存局部性被路由破坏   | 理论缓存容量充足，实际命中率低          | 缓存感知路由、会话亲和与热点均衡联合设计       |
| 量化或推测解码损伤质量 | 速度提高但任务成功率下降                | 建立质量门禁，报告净 Goodput 而非原始速度      |
| 在线与离线相互干扰     | 离线高吞吐导致在线尾延迟失控            | 分池、配额、时间窗和可抢占策略                 |
| 软件版本漂移           | 同样配置无法复现，升级后性能或质量回退  | 全栈版本台账、配置快照、回归、灰度和回退       |
| 敏感数据进入观测平台   | 合规和泄露风险                          | 默认脱敏、最小采集、租户隔离和访问审计         |
| 将研究收益当作商业承诺 | 验收争议和投资误判                      | 所有收益在目标环境实测，明确基线和适用条件     |

## 11. 结论

算力产业的竞争焦点正在从硬件资产规模转向有效服务产能。对多数行业智算中心而言，推理运营不是设备交付后的附属工作，而是决定资产能否转化为业务价值的核心环节。

一套成熟的算力运营体系应形成五项基本能力：

1. **看得清业务：** 能将应用拆解为可测量的推理负载和 SLO；
2. **算得准产能：** 能以真实轨迹和吞吐—延迟曲线确定有效容量；
3. **调得动系统：** 能协同模型、引擎、缓存、调度、并行和网络优化；
4. **守得住质量：** 能在性能优化中保持结果质量、尾延迟和稳定性；
5. **算得过成本：** 能以单位有效 Token 成本和每瓦有效 Token 产出评价长期运营。

最终目标不是让设备始终处于“忙碌”状态，而是让每一份硬件、能源和运维投入都尽可能转化为**满足质量与时延要求的有效智能服务**。这也是从“建算力”走向“运营算力”、从“卖卡时”走向“交付 Token 服务”的根本变化。
